# Harness Maturity Ladder

This ladder defines how `harness-engineering` progresses from static agent
instructions to measurable harness improvement. A level is achieved only when
its criteria can be inspected in repository files, durable Harness records, or
validation output.

## Levels

### H0 - Bare Environment

The model operates with no repository harness. It receives a prompt and may
produce a patch, but the repo does not tell it how to classify, validate, or
record work.

Criteria:

- No `AGENTS.md` Harness entrypoint exists.
- No feature intake policy exists.
- No story, decision, validation, or trace artifact exists.

Current status:

- Passed. This repository is beyond H0.

### H1 - Scaffolding And Policy

The repository contains static operating instructions, templates, risk lanes,
and source-of-truth rules. Agents can follow a documented workflow.

Criteria:

- `AGENTS.md` points agents to the Harness operating docs.
- `_harness/HARNESS.md`, `_harness/FEATURE_INTAKE.md`, and
  `_harness/ARCHITECTURE.md` exist.
- Story, decision, and validation templates exist under `_harness/templates/`.
- `_harness/TEST_MATRIX.md` defines fallback proof columns and status meanings.

Current status:

- Achieved.

Activated responsibilities:

- Task specification.
- Permissions.
- Project memory.
- Verification.

### H2 - Durable State And Observability

The repository has structured operational records and explicit observation
rules. Agents can record what happened, connect work to stories, and write
traces with predictable depth.

Criteria:

- `_harness/bin/harness-cli` records intake, story, decision, backlog, and trace
  data in `harness.db`.
- `_harness/scripts/schema/001-init.sql` defines durable tables for intake,
  story, decision, backlog, and trace records.
- `_harness/TRACE_SPEC.md` defines trace fields, quality tiers, and friction
  capture.
- `_harness/CONTEXT_RULES.md` defines phase-by-lane context rules.

Current status:

- Achieved.

Activated responsibilities:

- Task state.
- Observability.
- Failure attribution.
- Context selection.
- Entropy auditing.

### H3 - Active Observability And Evolution

The harness can evaluate its own operational data and turn repeated failures
into prioritized improvements.

Criteria:

- Trace quality can be scored by `_harness/bin/harness-cli score-trace`.
- Harness friction can be grouped with `_harness/HARNESS_COMPONENTS.md`.
- Backlog items include predicted impact and actual outcome after completion.
- Improvement proposals are generated by `_harness/bin/harness-cli propose`.

Current status:

- Partial. Trace scoring, friction queries, backlog outcome fields, audit, and
  proposal generation exist. Full H3 still requires benchmark comparison output
  that attributes regressions to harness components.

Activated responsibilities:

- Observability.
- Failure attribution.
- Entropy auditing.
- Intervention recording.

### H4 - Automated Verification

The harness can run or orchestrate proof checks consistently and can flag
incomplete work before the final response.

Criteria:

- Stories can store and execute a `verify_command`.
- `_harness/bin/harness-cli story verify <id>` records pass/fail state.
- `_harness/bin/harness-cli story verify-all` runs all configured story proof
  commands.
- Trace recording warns when a linked story has not passed verification.

Current status:

- Achieved by the CLI. The docs now expose this workflow under the `_harness/`
  layout.

Activated responsibilities:

- Verification.
- Task state.
- Permissions.
- Intervention recording.

### H5 - Self-Improving Harness

The harness can use traces, interventions, audit findings, and backlog outcomes
to propose safe improvements to itself.

Criteria:

- Repeated friction patterns are summarized into proposed harness changes.
- Proposed changes include predicted impact, risk, validation plan, and review
  posture.
- Completed changes compare predicted impact with actual trace, audit, or
  benchmark outcomes.
- High-risk harness changes pause before changing source hierarchy,
  architecture direction, validation requirements, or risk policy.

Current status:

- Partial. `_harness/bin/harness-cli audit`, `score-context`, `intervention`,
  and `propose` exist, and `_harness/IMPROVEMENT_PROTOCOL.md` documents the
  review loop. Full H5 requires repeated outcome proof.

Activated responsibilities:

- Entropy auditing.
- Failure attribution.
- Intervention recording.
- Permissions.
